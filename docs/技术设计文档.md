# 智能旅行规划助手 · 技术设计文档

> 版本：v1.0（2026-08-23）
> 状态：待评审。评审通过后按第 12 章里程碑开发，本文档是唯一设计依据，代码不得偏离本文定义。

---

## 1. 项目概述

### 1.1 要解决的问题

用户做旅行攻略时，需要在多个 App 之间反复横跳：查景点、找餐厅、比酒店、估预算，信息分散且费时，最后预算还经常超。

本系统让用户只输入一句话（如"国庆去成都玩3天，预算3000，喜欢美食"），就得到一份**结构完整、预算可控、可手动微调**的行程单。

### 1.2 方案一句话

3 个 Agent 顺序协作：**Planner（规划）→ Info（信息）→ Budget（预算）**，Agent 之间用 JSON 传结构化数据，预算超标时回环调整，任何工具故障都有兜底数据，保证流程不中断。

### 1.3 核心指标（评估目标）

| 指标 | 单 LLM 直出（基线） | 本系统（目标） |
|---|---|---|
| 行程合理率（50 条测试用例） | ~50% | ≥85% |
| 平均耗时 | ~5s | ≤15s |
| 单任务 LLM 成本 | ~0.02元 | ≤0.15元 |

合理率、用例集、打分标准的定义见第 11 章。

### 1.4 设计原则（写给面试官和后来的自己）

1. **不炫技**：不用任何 Agent 框架（LangChain 等），编排逻辑手写，核心代码控制在 1000 行以内，任何人 10 分钟能读完主流程。
2. **能用规则不用 LLM**：只有"参数抽取"和"行程编排"两处必须用 LLM，子任务生成、费用估算、预算调整全部是确定性代码。省成本、结果稳定、好测试。
3. **故障是常态**：每一个外部依赖（哪怕是本地工具模块）都有超时、重试、兜底三层处理。
4. **数据全部离线**：所有工具（天气/景点/美食/酒店）为本地离线实现，但**接口形状按真实 API 设计**（异步、可超时、可失败），将来接真实 API 只改 `tools/` 目录，Agent 层零改动。

## 2. 需求定义

### 2.1 功能需求（FR）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR1 | 需求理解：从一句话中抽取目的地、天数、预算、出发城市、日期、偏好、人数 | 抽取结果符合 5.2 节 `TravelRequest` schema；目的地缺失时向用户追问一次 |
| FR2 | 子任务拆解：把需求拆成查景点、查美食、查酒店三个子任务 | 子任务数量固定为 3，数量规则见 6.1 节 |
| FR3 | 信息获取：为每个子任务返回结构化候选数据 | 数据符合 5.3 节 schema，含来源标记（local / fallback） |
| FR4 | 行程编排：把候选数据组装成按天、按时段（上午/下午/晚上）的行程 | 符合 5.6 节 `Itinerary` schema；雨天优先室内景点；同一天景点尽量同区域 |
| FR5 | 预算校验：估算总费用并分项列出；超标则回环调整 | 估算规则见第 8 章；回环最多 2 轮，仍超标则输出"预算过紧"提示和最低可行预算 |
| FR6 | 行程单输出：同时输出结构化 JSON 和可读文本 | 文本行程单可直接阅读，含每日安排、酒店、预算报告 |
| FR7 | 人工调整：行程单输出后，用户可替换景点、调整酒店档次、修改预算 | 调整只触发 Budget 重算（必要时 Info 补充候选），不重跑全流程 |
| FR8 | 故障兜底：工具层数据缺失或故障时返回兜底数据 | 流程不中断，行程单 `meta.data_source` 标注 fallback |

### 2.2 非功能需求（NFR）

| 编号 | 需求 | 指标 |
|---|---|---|
| NFR1 | 耗时 | 复杂请求（≥3天）端到端 ≤15s |
| NFR2 | 成本 | 单任务 LLM 成本 ≤0.15元（LLM 调用次数收敛在 2~4 次） |
| NFR3 | 可用性 | 任一工具模块故障不影响最终输出（降级为兜底数据） |
| NFR4 | 可读性 | 无框架依赖；运行依赖仅 `openai`、`pydantic` 两个包 |
| NFR5 | 环境 | Python 3.12，uv 管理依赖；除 LLM API 外完全离线可跑 |

### 2.3 非目标（明确不做）

- 不做订票、下单、支付。
- 不做跨国、多城市连玩（一次请求只有一个目的地）。
- 不做实时价格（酒店/门票价格用离线数据中的静态估价）。
- 不做并发优化（三个子任务顺序执行，并发作为后续优化项）。
- 不做 Web 界面，v1 只做命令行（CLI）。

### 2.4 典型用例

| 用例 | 用户输入 | 预期行为要点 |
|---|---|---|
| U1 标准请求 | "国庆去成都玩3天，预算3000，喜欢美食" | 完整三 Agent 流程；偏好"美食"体现为餐厅和美食类景点权重更高 |
| U2 低预算 | "去西安穷游3天，预算800" | 首轮估算超标 → 自动降酒店档次、换免费景点 → 或两轮后提示预算过紧 |
| U3 信息不全 | "想去杭州玩几天" | 追问天数（和预算），补全后继续 |
| U4 人工调整 | U1 输出后，用户选择"替换第2天下午的景点" | 仅重算预算并展示新行程单 |
| U5 简单请求 | "去北京玩1天" | v1.1 起走单 LLM 直出，不进多 Agent 流程（见 3.4 节） |

## 3. 系统架构

### 3.1 架构图

```
用户输入（一句话）
        │
        ▼
┌─────────────────┐
│  Planner Agent  │ ① LLM 抽取参数（TravelRequest）
│                 │ ② 代码生成 3 个子任务（SubTasks）
└───────┬─────────┘
        │ JSON: SubTasks
        ▼
┌─────────────────┐
│   Info Agent    │ ③ 逐个调用本地工具（天气/景点/美食/酒店）
│                 │    失败 → 兜底数据，标注 source=fallback
└───────┬─────────┘
        │ JSON: InfoResult[]
        ▼
┌─────────────────┐
│  Planner Agent  │ ④ LLM 编排行程（Itinerary）
└───────┬─────────┘
        │ JSON: Itinerary
        ▼
┌─────────────────┐
│  Budget Agent   │ ⑤ 代码估算费用、判定 ok/over/under
│                 │    超标 → 生成调整建议（suggestions）
└───────┬─────────┘
        │ over? ─── 是 ──▶ Planner 代码执行调整 ──▶ Budget 复检
        │ 否（或已满2轮）
        ▼
   输出行程单（JSON + 文本）
        │
        ▼
   人工调整循环（FR7）──── 调整后仅 Budget 重算
```

### 3.2 Agent 职责表

| Agent | 职责 | 用 LLM 的步骤 | 纯代码的步骤 |
|---|---|---|---|
| Planner | 需求理解、子任务拆解、行程编排、执行预算调整 | 参数抽取（1次）、行程编排（1次） | 子任务生成、调整执行 |
| Info | 调用工具层获取结构化数据，负责重试与兜底 | 无 | 工具调用、超时重试、兜底 |
| Budget | 费用估算、合理性判定、调整建议 | 无 | 估算、判定、建议生成 |

> 面试讲法：不是所有环节都用 LLM。LLM 只做两件它擅长的事（理解模糊输入、做有审美的编排），算钱和拆任务这种确定性逻辑用代码，又快又稳又免费。

### 3.3 编排流程（orchestrator.py 伪代码）

```python
def plan(user_input: str):
    req = planner.extract_request(user_input)        # LLM ①
    tasks = planner.make_subtasks(req)               # 代码 ②
    results = info_agent.run(tasks)                  # ③ 每个工具：超时→重试1次→兜底
    itinerary = planner.compose_itinerary(req, results)   # LLM ④
    report = budget.check(req, itinerary)            # 代码 ⑤

    for round in range(MAX_ADJUST_ROUNDS):           # MAX_ADJUST_ROUNDS = 2
        if report.status != "over":
            break
        itinerary = planner.apply_suggestions(itinerary, report.suggestions)  # 代码
        report = budget.check(req, itinerary)

    return render(itinerary, report)                 # 文本渲染，代码
```

### 3.4 简单请求路由（v1.1 迭代项，v1 不实现）

评估发现：1~2 天的简单请求走多 Agent 反而比单 LLM 直出慢且贵。v1.1 在入口加一行路由：

```python
if req.days <= 2:
    return direct_generate(req)    # 单 LLM 直出，跳过 Info/Budget
```

本文档其余部分描述 v1；路由作为第 12 章的迭代项，避免过早设计。

## 4. Agent 详细设计

### 4.1 Planner Agent（agents/planner.py）

**方法一：`extract_request(user_input) -> TravelRequest`（LLM）**
- Prompt 要求模型只输出 JSON，字段见 5.2 节。
- 输出经 pydantic 校验；校验失败 → 把错误信息拼回 Prompt 重试 1 次；再失败 → 抛 `ExtractError`，CLI 层向用户追问缺什么补什么（不整句重来）。
- 目的地抽取不到：不重试，直接进入追问流程（问目的地）。

**方法二：`make_subtasks(req) -> list[SubTask]`（代码，模板化）**

| 子任务 | type | 数量规则 |
|---|---|---|
| 查景点 | attractions | 候选数 = days × 3 |
| 查美食 | food | 候选数 = days × 2 |
| 查酒店 | hotels | 固定 5 个（覆盖三档价位） |

**方法三：`compose_itinerary(req, results) -> Itinerary`（LLM）**
- 输入：TravelRequest + 候选数据 + 模拟天气。
- Prompt 中的硬约束（写进系统提示）：
  1. 每天安排上午/下午/晚上三段，其中晚上允许是"夜市/自由活动"；
  2. 每天选 2~3 个景点，只能从候选列表选，不得编造；
  3. 每天安排午餐、晚餐各一家，只能从候选列表选；
  4. 雨天（`weather.rain == true`）优先选 `indoor == true` 的景点；
  5. 同一天的景点尽量同 `area`；
  6. 偏好命中的候选优先安排；
  7. 全程只选 1 家酒店；
  8. 只输出 JSON。
- 输出经 pydantic 校验，失败重试 1 次；再失败 → **降级**：用代码模板编排（按评分降序、按时长装箱），并在 `meta.degraded = true` 标注。

**方法四：`apply_suggestions(itinerary, suggestions) -> Itinerary`（代码）**
- 逐条执行 Budget 给出的建议（见 8.3 节），确定性替换，不调用 LLM。

### 4.2 Info Agent（agents/info.py）

**`run(tasks) -> list[InfoResult]`**
- 对每个 SubTask 调用 `tools/` 下对应工具；顺序执行。
- 每次调用：超时 3 秒（本地工具其实很快，超时参数是为了保留真实 API 的行为形状）→ 失败重试 1 次 → 仍失败用兜底数据，`source = "fallback"`。
- 返回结果附带 `weather`（天气工具按 destination + 日期逐天生成）。
- **故障注入开关**：环境变量 `SIMULATE_TOOL_FAILURE=1` 时，工具层以 50% 概率抛错，用于演示和测试兜底逻辑（面试演示用）。

### 4.3 Budget Agent（agents/budget.py）

**`check(req, itinerary) -> BudgetReport`（代码）**
- 按第 8 章规则估算分项费用，判定 `ok / over / under`。
- `over` 时按优先级生成调整建议（最多 3 条）；`under` 时给出一条升级提示（不强制调整）。

## 5. 通信协议（JSON Schema 全量定义）

> 所有 Agent 间消息用统一信封包裹，字段如下。 schemas.py 中的 pydantic 模型与本章一一对应，模型即文档。

```json
{ "msg_type": "subtasks | info_result | itinerary | budget_report | adjust_request",
  "sender": "planner | info | budget | user | orchestrator",
  "receiver": "planner | info | budget | user | orchestrator",
  "payload": { ... } }
```

### 5.1 用户输入（原始文本，不进信封）

```json
{ "text": "国庆去成都玩3天，预算3000，喜欢美食" }
```

### 5.2 TravelRequest（Planner 抽取结果）

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| destination | string | 是 | — | 城市名；抽不到则触发追问 |
| days | int | 是 | 3 | 1~7；超出范围按边界取整并提示 |
| budget | int | 是 | 3000 | 人均预算，元 |
| departure_city | string? | 否 | null | 提供则估算城际交通 |
| date | string? | 否 | null | 形如 2026-10-01；null 表示日期未定，天气按当月典型值 |
| preferences | string[] | 否 | [] | 枚举：美食/人文/自然/亲子/购物/夜生活/小众 |
| party_size | int | 否 | 1 | 人数，用于展示 |

示例：
```json
{ "destination": "成都", "days": 3, "budget": 3000,
  "departure_city": null, "date": "2026-10-01",
  "preferences": ["美食"], "party_size": 1 }
```

### 5.3 SubTask 与 InfoResult

SubTask（Planner → Info）：
```json
{ "task_id": "T1", "type": "attractions",
  "destination": "成都",
  "count": 9,
  "filters": { "preferences": ["美食"], "indoor_only": false } }
```
`type` 枚举：`attractions / food / hotels`。

InfoResult（Info → Planner）：
```json
{ "task_id": "T1", "type": "attractions", "source": "local", "data": [ ... ], "error": null }
```
- `source` 枚举：`local`（正常读取）/ `fallback`（兜底数据）。
- `data` 元素结构按 type 分三种，见下。

**景点 Attraction：**
| 字段 | 类型 | 说明 |
|---|---|---|
| name | string | 名称 |
| tags | string[] | 从偏好枚举 + 以下扩展取值：免费/街区/公园/博物馆/观景/户外 |
| price | int | 门票估价，元（免费为 0） |
| duration_hours | float | 建议游玩时长 |
| indoor | bool | 是否室内 |
| rating | float | 离线评分 4.0~5.0 |
| area | string | 城市内区域，如"青羊区" |

**餐厅 Restaurant：**
| 字段 | 类型 | 说明 |
|---|---|---|
| name | string | 名称 |
| tags | string[] | 菜系/品类，如 川菜/火锅/小吃/甜品 |
| price_per_person | int | 人均，元 |
| meals | string[] | 适合餐段，枚举 lunch/dinner |
| rating | float | 同上 |
| area | string | 同上 |

**酒店 Hotel：**
| 字段 | 类型 | 说明 |
|---|---|---|
| name | string | 名称 |
| tier | string | 枚举：经济型/舒适型/高档型 |
| price_per_night | int | 每晚价格，三档价位区间见 7.2 节 |
| area | string | 同上 |
| tags | string[] | 如 交通方便/近地铁 |

**天气 Weather（Info 附带返回，逐天）：**
```json
{ "city": "成都", "date": "2026-10-01",
  "condition": "小雨", "temp_low": 16, "temp_high": 22, "rain": true }
```
- `condition` 枚举：晴/多云/阴/小雨/大雨。
- 生成规则（tools/weather.py，确定性、可复现）：`seed = hash(city + date)`，按"城市-月份气候表"的权重随机选 condition，温度在气候表区间内取整。同一 city+date 永远得到相同结果。

### 5.4 Itinerary（Planner 编排结果）

```json
{
  "destination": "成都",
  "hotel": { ...Hotel },
  "days": [
    {
      "day": 1,
      "date": "2026-10-01",
      "weather": { ...Weather },
      "morning":   { "attraction": { ...Attraction } },
      "afternoon": { "attraction": { ...Attraction } },
      "evening":   { "text": "锦里夜市", "restaurant": { ...Restaurant } },
      "meals": { "lunch": { ...Restaurant }, "dinner": { ...Restaurant } }
    }
  ],
  "meta": { "data_source": "local", "adjust_rounds": 0, "degraded": false }
}
```
- `evening` 允许只有 `text`（自由活动）或 `restaurant`（夜市/晚餐），不强制安排景点。
- `morning/afternoon` 必须有 attraction；单日总时长（各景点 duration_hours 之和）≤8 小时。

### 5.5 BudgetReport（Budget 输出）

```json
{
  "status": "ok",
  "budget": 3000,
  "estimated_total": 1980,
  "breakdown": {
    "transport_intercity": 0,
    "transport_city": 150,
    "lodging": 640,
    "food": 690,
    "tickets": 120,
    "misc": 160
  },
  "suggestions": [
    { "action": "downgrade_hotel", "from_tier": "舒适型", "to_tier": "经济型" },
    { "action": "replace_paid_attraction", "target": "武侯祠", "reason": "门票50元，可换免费景点" }
  ],
  "note": "预算充裕，可升级酒店档次或增加付费体验"
}
```
- `status` 枚举：`ok / over / under`（判定阈值见 8.2 节）。
- `suggestions` 元素 `action` 枚举：`downgrade_hotel / replace_paid_attraction / reduce_daily_activities / none`。

### 5.6 端到端示例（U1 用例的消息流，节选）

```
用户        → "国庆去成都玩3天，预算3000，喜欢美食"
planner → info    subtasks:        [T1 attractions×9, T2 food×6, T3 hotels×5] + weather(成都, 10-01~03)
info    → planner info_result[3]:  source=local, 各候选列表
planner → planner itinerary:       3天行程（锦里、宽窄巷子、大熊猫基地…+ 每日午晚餐）
budget  → planner budget_report:   status=ok, estimated_total≈1980
输出：文本行程单 → 进入人工调整循环
```

## 6. 数据与工具层（tools/，全部离线）

### 6.1 数据文件与规格

```
src/travel_planner/data/
├── cities/            # 每城市一个文件：beijing.json / chengdu.json / ...
│   └── { attractions: [8~12], restaurants: [10~14], hotels: [5~8],
│         climate: { "10": { "conditions": {"阴":0.3,"小雨":0.3,"多云":0.3,"晴":0.1},
│                              "temp_low": 14, "temp_high": 22 } } }
└── fallback.json      # 通用兜底：热门城市通用景点/餐厅/酒店各若干 + 通用气候表
```

- 首批覆盖 10 个城市：北京、上海、成都、西安、杭州、重庆、长沙、青岛、南京、广州。
- 数据可用 LLM 辅助生成后**人工核对**，价格必须落在 7.2 节的档位区间内，tags 必须取自 5.3 节枚举。
- 数据验收：pydantic 校验通过 + 价格/评分落在规定区间。

### 6.2 工具接口（统一形状，为将来接真实 API 留口）

```python
class ToolResult(TypedDict):
    source: str          # "local" | "fallback"
    data: list[dict]

async def get_attractions(city: str, count: int, filters: dict) -> ToolResult: ...
async def get_restaurants(city: str, count: int) -> ToolResult: ...
async def get_hotels(city: str, count: int) -> ToolResult: ...
async def get_weather(city: str, dates: list[str]) -> ToolResult: ...
```

每个工具内部：读离线数据 → 按 filters 过滤 → 按 rating 降序取 count 条；数据不足 count 条就返回实际条数（不报错）；城市无数据文件 → 抛 `CityNotFoundError`，由 Info Agent 捕获后走 fallback。

## 7. 预算估算规则（Budget Agent，纯代码）

### 7.1 分项估算（人均）

| 分项 | 规则 |
|---|---|
| transport_intercity | 若 `departure_city` 非空：查内置城市距离表，高铁二等座按 0.45 元/km × 往返；无出发城市则为 0 |
| transport_city | 50 元/天 × days |
| lodging | 选中酒店 `price_per_night` × (days − 1) 晚 |
| food | 早餐 15 元/天 × days + 所选午/晚餐餐厅 `price_per_person` 之和 |
| tickets | 所选景点 `price` 之和 |
| misc | 以上五项之和 × 10%（机动预留） |
| **estimated_total** | 六项之和 |

### 7.2 酒店档位价位区间（离线数据生成约束，也是降档依据）

| 档位 | 每晚价格区间 |
|---|---|
| 经济型 | 150~300 |
| 舒适型 | 300~600 |
| 高档型 | 600~1200 |

### 7.3 城际距离表（节选，0.45 元/km 往返）

出发城市-目的地不足 10 个组合时，按"同区域 500km / 跨区域 1200km"的粗略规则估算，误差可接受（面试时明说是粗估）。

## 8. 合理性判定与调整策略

### 8.1 判定阈值

| 条件 | status | 行为 |
|---|---|---|
| estimated_total > budget × 1.05 | over | 生成调整建议，回环 |
| estimated_total < budget × 0.5 | under | 输出升级提示，不回环 |
| 其余 | ok | 直接输出 |

### 8.2 调整建议优先级（Budget 生成，Planner 执行）

1. 住宿占比（lodging / estimated_total）> 40% → `downgrade_hotel`：降一档，选该档候选中最低价。
2. 仍有付费景点 → `replace_paid_attraction`：按 price 降序每次最多替换 2 个为免费/低价候选。
3. 仍超 → `reduce_daily_activities`：每天景点数压到 2 个。
4. 两轮后仍超 → `status` 保持 over，`note` 输出"预算过紧，最低可行预算约 X 元"（X = 当前估算值）。

### 8.3 调整回环上限

`MAX_ADJUST_ROUNDS = 2`。回环中只执行建议（代码替换）+ Budget 复检，**不再调用 LLM**，保证调整轮的耗时和成本几乎为零。

## 9. 失败处理与降级（总表）

| 故障点 | 检测方式 | 处理（三层：重试→兜底→降级） | 用户可见 |
|---|---|---|---|
| 工具读数据失败/城市缺数据 | 抛 CityNotFoundError / OSError | 重试 1 次 → fallback.json 兜底 | 行程单标注 `source: fallback` |
| LLM 超时/网络错误 | openai SDK 异常 | 重试 1 次 | 报错并提示检查 Key/网络 |
| LLM 输出非法 JSON / 校验失败 | pydantic ValidationError | 错误信息拼回 Prompt 重试 1 次 → **降级**：参数抽取失败→追问用户；编排失败→代码模板编排 | `meta.degraded: true`，文本行程单末尾注明"本次为降级生成" |
| 预算两轮仍超标 | status == over | 停止回环，输出提示与最低可行预算 | 明确的中文提示 |
| 演示故障注入 | 环境变量 SIMULATE_TOOL_FAILURE=1 | 工具 50% 概率抛错，走兜底 | 同兜底路径 |

## 11. 测试与评估方案

### 11.1 用例集（50 条）

10 城市 × 5 形态：

| 形态 | 示例 | 考察点 |
|---|---|---|
| 标准 | "成都3天预算3000" | 主流程 |
| 低预算 | "西安3天预算800" | 超标回环/降档/预算过紧提示 |
| 高预算 | "上海3天预算8000" | under 提示 |
| 特殊偏好 | "长沙2天，带娃，喜欢自然" | 偏好命中、过滤 |
| 边界 | "北京1天预算200" / "广州7天预算2500" | 天数边界、长行程 |

### 11.2 合理性评分（checklist，自动打分）

每条用例按以下 10 项打分（各 1 分），**≥7 分记为"合理"**：

1. 每天景点数在 1~4 之间；
2. 每天有午餐和晚餐推荐；
3. 全程恰好 1 家酒店；
4. 住宿晚数 = days − 1；
5. 估算总费用与预算偏差 ≤ 15%（over 且两轮未解决的记 0 分）；
6. 景点、餐厅无重复；
7. 偏好标签在行程中命中次数 ≥ days（无偏好时记 1 分）；
8. 雨天不安排 `indoor == false` 的纯户外景点（无雨天时记 1 分）；
9. 每天景点总时长 ≤ 8 小时；
10. 输出为合法 JSON 且必填字段齐全。

### 11.3 对比实验

- 基线：同一 LLM、单一 Prompt 直出行程（不给候选数据，不让它算预算）。
- 记录：合理率、端到端耗时、LLM 调用次数与 token 数、折算成本。
- 输出 `docs/评估报告.md`：50 条明细 + 汇总表 + 失败案例分析。

## 13. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 输出不稳定导致行程不合法 | pydantic 强校验 + 定向重试 + 代码模板降级（9 章三层） |
| 离线数据被质疑"不是真 API" | 工具接口按真实 API 形状设计（异步+超时+兜底），替换真实源只改 tools/ 层；这是明确的架构决策，写在 1.4 节 |
| 成本超预期 | LLM 调用点收敛为 2 处；调整回环零 LLM；token 用量在评估报告里如实披露 |
| 评估主观 | checklist 全部可自动判定（11.2 节），脚本可复现 |
