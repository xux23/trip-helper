# 面试问答要点

> 用途：面试前的讲述提纲 + 预设追问的标准答案。
> 注意：文中"实测数字"（50%→85%、5s→12s、0.08元/次）是**目标口径，以 M6 产出的《评估报告》实测数据为准**，评估做完后必须替换成真实数字，面试前核对一遍。
> 数据源已从离线改为**高德在线**（含免费配额保护），并新增搜索模式、免费网页搜索、穷游学生取向（学生票/团购），本提纲已同步。

## 1. 一分钟版本（电梯陈述）

"我做了一个多 Agent 旅行规划助手：一句话进、完整行程单出、预算可控。比如'国庆去成都玩3天预算3000'——三个 Agent 顺序协作：Planner 理解需求并编排行程，Info 从**高德在线 API** 拿真实的景点/美食/酒店/天气数据，Budget 算钱，超预算就回环让 Planner 调整。数据源是真实在线的，带**免费配额保护**——高德个人 Key 有每日额度，超了程序直接停下来提示，绝不产生费用。Agent 间全用 JSON 通信，任何工具挂了都有兜底，流程不断。另外支持'找成都免费景点'这种**输入即搜索**，结果末尾还会附带免费的网上攻略摘录。整个系统只有两处用 LLM，拆任务、算钱、调预算全是确定性代码。对比单 LLM 直出，行程合理率从约 50% 提到 85%（目标口径），等待过程有转圈动画和实时耗时显示。"

## 2. STAR 展开

- **任务（痛点）**：普通人（尤其穷游学生）做旅行攻略要在多个 App 间横跳，信息分散、预算容易超。目标：一句话进、完整行程单出、预算可控、符合学生党"省钱但不牺牲特色"的玩法。
- **基线**：同一个 LLM 单次直出行程，50 条测试用例上合理率约 50%——常见问题是编造景点、预算严重失真、一天塞 6 个景点。
- **方案**：3 个 Agent 顺序协作 + JSON 通信 + 预算兜底回环；**数据源用高德在线 API**（POI/天气，词表映射为 schema，免费配额保护）；搜索模式直接出景点列表 + 必应中国免费网页攻略摘录；"穷游但不穷玩"取向（学生票半价、团购价、平价特色店优先，但必打卡地标不省）。关键取舍：**只有两处用 LLM**（参数抽取、行程编排），子任务拆解、费用估算、预算调整全是确定性代码。
- **个人贡献**：独立完成全部设计开发；最有含金量的是 LLM/代码的成本划分（哪步用 LLM、哪步用代码）、Budget 的费用估算规则（分项公式 + 调整优先级 + 2 轮回环上限）、高德 POI→schema 映射与免费配额保护、搜索模式的短路分支。
- **结果**：50 条用例，任务合理率 50%→85%（目标）；平均耗时大头是 LLM 调用本身（慢服务商编排单次可能 40s+，已放宽超时并加等待动画）；单任务成本约 0.08 元（LLM 调用收敛在 2~3 次）。
- **反思**：1~2 天的简单请求走多 Agent 又慢又贵，v1.1 加路由：≤2 天直接单 LLM 生成。另一个教训是**预算不现实要诚实提示**——回环后仍超标的预算不该硬凑行程，而是给出最低可行预算和同类比价，把决策交还用户。

## 3. 预设追问 Q&A

**Q1：为什么不用 LangChain / AutoGen 这类框架？**
项目规模小，框架带来的抽象层比业务逻辑本身还复杂。手写编排器只有约 40 行，每一行都能讲清楚；不依赖框架反而逼我把 Agent 边界、通信协议、失败处理想明白。这本身就是这个项目的学习目的。

**Q2：为什么是 3 个 Agent，不是 1 个或 5 个？**
按职责单一原则切：规划（理解+编排）、信息（取数+兜底）、预算（算钱+校验）是三种性质不同的工作——前两种要 LLM/外部数据，第三种是纯规则。1 个 Agent 职责混杂、prompt 臃肿；再加 Agent（比如单独的"天气 Agent"）没有独立决策点，只会增加通信开销。

**Q3：Agent 间为什么用 JSON 通信而不是自然语言？**
自然语言传递会有信息损耗和解析不确定性。JSON + pydantic 强校验，下游拿到的数据要么合法要么触发重试，失败路径清晰。统一的消息信封（msg_type/sender/receiver/payload）也方便打日志排查。

**Q4：为什么用高德 POI 搜索，而不是普通网页搜索当数据源？**
高德 `place/text` 返回的是**结构化 POI**（名称/分类/评分/人均/行政区），直接能填进 pydantic schema、算进预算报告；普通网页搜索返回的是网页摘要，要自己解析实体，不可靠也不能算钱。所以数据源用高德，**网页搜索只做辅助**——搜索模式末尾用必应中国（国内可直连、免 Key）拉"攻略摘录"当参考，失败了也不影响核心结果。

**Q5：高德免费配额怎么保护，不会超支吗？**
`QuotaTracker` 按服务（search/geocode/weather）每日计数，持久化到 `.amap_quota.json`（跨重启累计、日期自动清零）；每次请求前检查，**超限抛 `QuotaExhaustedError` 直接停止整个程序**（启动时检查 + 运行中超限都会停，exit 3），加上 0.4s 节流防 QPS 限流。限额在 `.env` 配置，默认保守值，可对齐自己 Key 的真实免费档位。宁可停，不静默多打一次。

**Q6：门票/房价是估算的，可信吗？**
高德 POI 接口没有门票价和房价字段，所以用分类词表估算并**在结果里诚实标注"价格估算"**；穷游学生出行还会自动按**学生票（景点普遍半价）和团购价（餐饮普遍 8.5 折）**估算，贴近真实开销。接高德门票服务市场 API 或 OTA 房价接口时，只改映射函数，上层不动。

**Q7：LLM 输出不稳定怎么办？**
三层：pydantic 校验 → 把校验错误拼回 Prompt 定向重试 1 次 → 降级到代码模板（行程编排）或追问用户（参数抽取）。**编排阶段 LLM 网络/超时也直接降级模板**，不崩流程。降级生成的行程会在输出里明确标注。实测绝大部分失败在第一层重试就解决。

**Q8：多 Agent 比单 LLM 慢，为什么还要用？**
慢换来的是合理率和可控性：候选数据约束住了幻觉，预算回环约束住了开销。耗时大头是两次 LLM 调用的固有延迟（慢服务商编排单次可能 40s+，已把超时放宽到可配置的 180s，并用转圈动画+实时耗时让等待可见），回环调整是纯代码几乎零耗时。对 3 天以上的复杂行程，用户对等待不敏感。

**Q9：预算回环为什么上限 2 轮？**
实测超标场景一轮降档/换平价特色店就能解决；两轮还超说明预算本身不现实，继续循环只会浪费时间。此时**不硬排行程**，提示"预算不现实"：给出最低可行预算、折算每天开销、同类比价（几杯奶茶/几顿火锅）和建议预算档位，把决策交还用户。

**Q10："穷游但不穷玩"怎么落地？**
三层配合：① 编排 Prompt 明确定义旅行观——能省的地方省（交通/住宿/非特色景点），该花的地方花（当地特色美食、必打卡地标）；② 确定性兜底——预算偏紧默认经济型酒店、正餐超人均 70 元自动换平价特色店、学生票/团购价估算；③ 预算回环在"别省过头"和"预算现实"之间兜底。省钱不是目的，把钱花在刀刃上是。

**Q11：如果要支持 100 并发，架构要改什么？**
编排器从同步改异步是第一步（接口已经按 async 设计）；三个子任务可以并发取数；再加结果缓存（同城市候选数据可缓存）；LLM 调用做限流和降级排队；高德配额做进程级共享计数。架构分层的好处是这些都只动编排层和工具层。

**Q12：这个项目最大的不足是什么？**
门票/房价是词表估算（高德 POI 无价格字段）；免费网页搜索依赖必应页面结构（布局变了可能解析不到）；维基/DDG 在国内网络不可达（已做成可配置源）；评估用例 50 条、合理性标准是自定 checklist，主观成分仍在，且评估报告还没实测。改进方向：接门票/OTA 房价 API、必应官方搜索 API、扩大用例集、引入人工评分交叉验证。
